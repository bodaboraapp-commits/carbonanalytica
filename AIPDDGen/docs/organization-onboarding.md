# Organization onboarding

**Status:** implemented (product-owner request, migration `migrations/0003_organization_onboarding.sql`).
**Scope:** a four-step wizard that collects an organization's legal details, primary contact and verification documents, then submits the workspace for verification.

The reference is the onboarding wizard many registry-facing SaaS products use: a horizontal progress rail (info → contact → documents → review), a declaration-template callout, dashed upload zones with the accepted formats, and a review screen that locks the profile on submit.

---

## Why it exists

Every draft a workspace produces is addressed to a registry (Gold Standard, Verra VCS). Registries and validators need to know **who** submitted the PDD and that the submitting organization is real. This wizard captures that identity once per workspace and gives reviewers a single place to approve or send back.

It is deliberately separate from the project pipeline: organization verification is a property of the **workspace (`team_id`)**, not of an individual PDD project.

---

## Routes

| Method | Path | Purpose |
| --- | --- | --- |
| GET | `/onboarding?step=1..4` | Wizard page. The requested step is clamped to the furthest reachable step. |
| POST | `/onboarding/organization` | Save step 1 (legal details). |
| POST | `/onboarding/contact` | Save step 2 (primary contact). |
| POST | `/onboarding/documents` | Upload or replace one document (`kind` + `document` file). |
| POST | `/onboarding/documents/{id}/delete` | Remove a document and its stored file. |
| GET | `/onboarding/documents/{id}` | View a document inline (PDFs render in the browser). |
| GET | `/onboarding/documents/{id}/download` | Download a document as an attachment. |
| POST | `/onboarding/submit` | Submit for verification (requires the attestation checkbox). |

All routes require a signed-in member. Writes require the **admin** role; owners and admins can submit. Viewers and editors get a read-only view.

## Steps and completion rules

| Step | Complete when |
| --- | --- |
| 1. Organization info | `legal_name`, `registration_number`, `registration_country`, `organization_type`, `registered_address`, `city` are set. |
| 2. Contact details | `contact_name`, `contact_role`, `contact_email`, `contact_phone` are set. |
| 3. Documents | All **required** document kinds are present (see below). |
| 4. Review | The profile status is `submitted` or `verified`. |

Steps are **derived from stored data**, not tracked in a wizard table: a refresh, a second admin or a re-opened tab always agrees on where the organization stands. `OnboardingService::furthestStep()` allows the first incomplete step plus one look-ahead.

## Required documents

| Kind | Required | Field in the reference UI |
| --- | --- | --- |
| `registration_certificate` | yes | Certificate of incorporation |
| `ownership_structure` | yes | CR-12 / ownership structure / officials list |
| `declaration` | yes | Signed declaration (template provided) |
| `tax_compliance` | no | Tax compliance certificate |

One current file per kind (`UNIQUE (team_id, kind)`). Uploading again replaces the file and deletes the previous one **after** the new row commits; the audit log records the replacement. The declaration template is a static asset: `public/assets/templates/organization-declaration-template.docx`, regenerated by `tools/generate-declaration-template.py`.

## Upload rules

- Extensions: **PDF, DOC, DOCX** (`Storage::ORGANIZATION_DOCUMENT_EXTENSIONS`).
- Product limit: 50 MB (`Storage::ORGANIZATION_DOCUMENT_MAX_BYTES`), lowered automatically to the lower of `upload_max_filesize` and `post_max_size`; the effective limit is shown next to every upload zone.
- The extension allowlist and the `finfo` MIME sniff must agree; the stored MIME is re-checked before it is echoed in a `Content-Type` header.
- Files live under `storage/uploads/organization/<year>/<month>/<uuid>.<ext>` with server-generated keys, so user input never becomes a path. `Storage::path()` rejects `..` keys.
- A POST body larger than `post_max_size` arrives with empty `$_POST`/`$_FILES`; the front controller detects it and returns a friendly 413 instead of a misleading CSRF error.

## Status flow and lock

```
draft ──submit──▶ submitted ──staff verify──▶ verified
   ▲                  │
   │                  └──staff reject (reason required)──▶ rejected
   │                                                          │
   └────────────────────── resubmit ◀────────────────────────┘
```

While `submitted` or `verified` the profile is locked: every write path (`saveOrganization`, `saveContact`, `uploadDocument`, `deleteDocument`, `submit`) raises a conflict. A `rejected` profile becomes editable again; the rejection reason is shown to the workspace and a **fresh review task** is created when the profile is submitted again. The previous review note stays visible in the submitted banner until the next decision replaces it.

Submission also records the attestation (`attested_at`, `attested_by_user_id`): the submitting admin confirms the information is accurate and that they are authorised.

## Admin review (`/admin/kyc`, staff only)

Staff decide on a submitted profile from the KYC queue: plain `?status=submitted|verified|rejected|all` filter chips plus a per-row `<details>` **Review decision** panel with two no-JS forms (`POST /admin/kyc/{profileId}/verify` and `/admin/kyc/{profileId}/reject`, CSRF protected).

- **Verify**: optional approval note (≤500 characters). Profile becomes `verified`, `reviewed_at` is set, the tenant stays locked.
- **Reject**: reason is **required** (≤500 characters, inline field error); the profile becomes `rejected`, unlocks for editing, and the reason is shown on the tenant onboarding banner and dashboard, together with an **Update & resubmit** CTA.
- The decision also completes the open `organisation_kyb` review task (the generic job-queue Complete action refuses KBY tasks and points staff to the KYC queue), and records audit entries.
- The primary contact (`organization_profiles.contact_email`) receives an EN/FR outcome email in the workspace owner's locale; email delivery is recorded in `email_outbox` and a mail failure never rolls back the recorded decision.

## Data

Two tables (see [data model](data-model.md#36-organization-onboarding-product-owner-request-migration-0003)):

- `organization_profiles` — one row per team (`UNIQUE team_id`), created lazily on first save.
- `organization_documents` — one row per document kind, with original filename, storage key, MIME type, size and SHA-256 checksum.

`registration_country` is stored as **free text** at launch (up to 80 characters) so any jurisdiction can onboard. ISO-3166 code normalisation remains a follow-up in the review console.

## Audit events

| Action | When |
| --- | --- |
| `organization.profile.updated` | Step 1 or 2 saved (`metadata.step` says which). |
| `organization.document.uploaded` | Document stored (`kind`, `filename`, `size_bytes`, `replaced`). |
| `organization.document.deleted` | Document removed (`kind`). |
| `organization.submitted` | Profile sent for verification (`legal_name`). |
| `organization.verified` | Staff approved the profile on the KYC queue (`note_length`, `tasks_closed`). |
| `organization.rejected` | Staff requested changes (`note_length`, `tasks_closed`; the reason is in `review_note`, not the audit metadata). |
| `review_task.completed` | A decision closed the linked `organisation_kyb` review task (`work_type`, `by=kyc_decision`). |

## Known limitations / follow-ups

- **No inline file preview for DOC/DOCX.** Browsers download them; the view link states this.
- **No drag-and-drop JavaScript.** The upload zone is a labelled file input: forms keep working without JavaScript, matching the rest of the app.
- **No virus scanning or OCR.** Documents are stored as uploaded; a scanner belongs with the production storage adapter.
- **No retention/erasure job** for rejected or replaced documents beyond immediate deletion of the replaced file. Workspace deletion cascades rows; the 30-day purge job is step 10.
- **One outcome email only**: no reminders, no reviewer assignment notifications. The decision itself is visible in the tenant workspace without email.
